Multica signs users in with an email address and password. Email ownership is not verified during registration. Existing users sign in with the password they created; signup controls only decide whether a new account can be created.

## Email and password

Choose **Create account** on the sign-in screen, enter an email address, and choose a password with at least 8 characters. After registration, use the same email and password to sign in.

<Callout type="warning">
Because registration does not verify email ownership, use `ALLOW_SIGNUP=false` together with an allowlist when access must be limited to a known group.
</Callout>

## Email delivery for invitations

Email delivery is not needed for password sign-in. Configure Resend or SMTP to deliver workspace invitation links and, during a temporary legacy-account migration, verification codes. When both are configured, `SMTP_HOST` takes priority.

### Using Resend

1. Verify a sending domain and create an API key at [Resend](https://resend.com/).
2. Set:

   ```dotenv
   RESEND_API_KEY=re_xxxxxxxxxxxxxxxx
   RESEND_FROM_EMAIL=noreply@example.com
   ```

3. Restart the API service.

`RESEND_FROM_EMAIL` must belong to a domain already verified in Resend.

### Using SMTP

At minimum, set the host and sender address:

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=multica
SMTP_PASSWORD=<password>
SMTP_FROM_EMAIL=noreply@example.com
```

| Scenario | Configuration |
|---|---|
| Internal anonymous relay | `SMTP_PORT=25`, leave username and password empty |
| STARTTLS | `SMTP_PORT=587`; upgrades to TLS by default when the server supports it |
| Implicit TLS | `SMTP_PORT=465`, or set `SMTP_TLS=implicit` explicitly |

If `SMTP_FROM_EMAIL` is unset, it falls back to `RESEND_FROM_EMAIL`. Private CAs or self-signed certificates require adding the CA to the container trust store; `SMTP_TLS_INSECURE=true` skips certificate verification and should only be used temporarily on a trusted internal network.

Without an email service, the server still starts, but it rejects new workspace invitations and legacy verification-code requests. Invitation links and verification codes are bearer credentials and are never written to logs.

Upgrading to this release expires all pending invitations created before capability tokens were introduced. Reissue any invitation that should remain valid after the upgrade.

## Signup restrictions

Three variables together decide whether a new account can be created:

| Variable | Effect |
|---|---|
| `ALLOWED_EMAILS` | Full email addresses allowed to sign up, comma-separated |
| `ALLOWED_EMAIL_DOMAINS` | Email domains allowed to sign up, comma-separated |
| `ALLOW_SIGNUP` | Whether signup is allowed when no allowlist is configured; defaults to `true` |

The evaluation order is:

1. The email matches `ALLOWED_EMAILS` - allow.
2. Or its domain matches `ALLOWED_EMAIL_DOMAINS` - allow.
3. With no match, if `ALLOW_SIGNUP=false` - reject.
4. With `ALLOW_SIGNUP=true` but any allowlist configured and no match - still reject.
5. With no allowlist configured and `ALLOW_SIGNUP=true` - allow.

Common configurations:

```dotenv
# Company domain only
ALLOW_SIGNUP=false
ALLOWED_EMAIL_DOMAINS=company.com

# Also admit one external collaborator
ALLOWED_EMAILS=partner@example.net
```

<Callout type="info">
Both allowlists also work as explicit exceptions when `ALLOW_SIGNUP=false`. A pre-provisioned account without a password cannot use public registration to set its initial password.
</Callout>

## Legacy account migration

Set `AUTH_LEGACY_AUTH_ENABLED=true` during a controlled compatibility window for installed clients and accounts created before password sign-in. The legacy email-code and Google endpoints authenticate only an existing account that has no password; they never create an account or change a password.

After a legacy user signs in with a delivered verification code, the web sign-in page asks them to set a password. Keep email delivery configured until those users have completed that step. If Google OAuth was used by an installed client before the upgrade, keep its existing `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and registered `GOOGLE_REDIRECT_URI` configured during the window.

Use the server telemetry for legacy routes, plus your client-release adoption data, to decide when to set `AUTH_LEGACY_AUTH_ENABLED=false` and restart the API. Disabled legacy routes return `410 Gone` so outdated clients receive an upgrade signal rather than an unexplained `404`.

## Session lifetime

Browser sign-ins last 30 days by default. Adjust with `AUTH_TOKEN_TTL`, which accepts a Go duration or a positive integer of seconds:

```dotenv
AUTH_TOKEN_TTL=720h
```

Restart the API service after changing it. The value only affects sign-in cookies and JWTs issued afterwards; it does not extend tokens that were already issued.
